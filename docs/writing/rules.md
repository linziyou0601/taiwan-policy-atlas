# 寫作規則

文件、程式註解、commit message 與 PR 描述怎麼組織與怎麼寫，以及寫作檢查列出的項目怎麼判讀。同一類的文件用同一副骨架，句子寫成熟悉這個領域的人會寫的樣子。適用於新增或修改任何一份文件與任何一則註解。每條規則的說明、判定問題與改法寫在 `scripts/writing/tables/` 的規則表，檢查的輸出會附上。

<br>

## 文件的骨架

每一類文件的章節固定，讀者換一份文件時在同樣的位置找到同樣的資訊。新增文件時先讀同一類的另一份，章節、表頭與引言的句型照它：

| 文件 | 骨架 |
|---|---|
| `README.md` | 定位、目錄、功能特色、資料範圍、技術棧、安裝與啟動、常用指令、產生與校驗腳本、專案結構、架構、使用方式、功能限制、資料來源、隱私權、版本與發行、文件入口、致謝、授權 |
| `CONTRIBUTING.md` | 目錄、內容分類、每種工作的步驟、程式寫法、本機驗證、分支規範、commit 與 PR、版本與發行、疑難排解 |
| `AGENTS.md` | 四章：文件權威順序、主題權威來源、鐵律、工作流入口。每章一個 H1，只導航，步驟與指令寫在它指向的文件 |
| `DESIGN.md` | front matter 加九章：Visual Theme and Atmosphere、Color Palette and Roles、Typography Rules、Component Stylings、Layout Principles、Depth and Elevation、Do's and Don'ts、Responsive Behavior、Agent Prompt Guide |
| `docs/pipeline/{階段}.md` | 一段說明這個階段把什麼變成什麼，再依序是輸入、步驟、判讀規則、核對、產物。沒有判讀的階段省略判讀規則 |
| `docs/` 的其餘文件 | 開頭一段寫這份文件回答的問題與適用的時機，再依主題分 H2。檔名結尾表示性質：`-policy` 是判斷的規則，`-protocol` 是依序執行的流程，`-contract` 是程式讀寫的格式 |

根目錄的文件寫寬的內容，`docs/` 寫細的內容，同一件事只寫在一處，其他地方以連結指過去。版面依下列規則：

- `README.md`、`CONTRIBUTING.md` 與 `docs/` 的文件各有一個 H1，H2 之間放空行、一行 `<br>` 與空行。`AGENTS.md` 與 `DESIGN.md` 每章一個 H1，章之間放三行 `<br>`、兩個空行與 `---`。
- 標題依 H1、H2、H3 逐層往下，最深到 H3。
- 流程的每一步以「完成判準如下：」引出一張表頭是條件、證據的表，每一列是一個可以判定的條件與確認它的方式。
- 連到 repo 內的檔案寫相對路徑，連到章節時連結文字寫「文件的章節」。
- 每一格都是短值的內容才寫成表格。一格要寫好幾句時，每一列改成一個三級標題加段落，讀者才不必在表格裡讀長文。

<br>

## 產物與段落

表格、程式碼區塊、編號清單、項目清單與圖都是前文的產物，基本的形態是「說明，然後產物」。產物之前的說明交代用途、讀法與適用的條件，產物本身列出完整的內容。產物之後直接接下一個標題，或接一段引出下一個產物的說明。條件寫在產物之後時，讀者照著表設定或照著指令執行完才看見。清單的項目內也一樣，步驟的說明與限制寫在指令的程式碼區塊之前。各種排法：

| 排法 | 判定 |
|---|---|
| 說明，產物 | 採用 |
| 說明一，產物一，說明二，產物二 | 採用 |
| 說明，產物，補述 | 把補述移到產物之前，或寫進產物 |
| 說明一，說明二，產物一，產物二 | 每個產物緊接在自己的說明之後 |

## 句子

句子直接陳述事實，一句接一句往下寫。下列寫法改成右欄的寫法：

| 寫法 | 改成 |
|---|---|
| 「不是 A，而是 B」，或正面的事實之後追加一句否定 | 只寫正面的事實 |
| 「本檔不處理」「不再使用」這類描述缺席的句子 | 寫現在由誰處理、現在用什麼 |
| 「原本」「改為」「此次」「目前」「暫時」這類描述變更經過的用語 | 寫現在的行為，經過寫在 commit message |
| 句內以粗體強調，或以「務必」「非常重要」加重 | 寫出沒有照做的後果 |
| 「例如」之後列出一部分，或以「等」收尾 | 全部列出，或改用涵蓋全部的上位詞 |
| 開場的暖場句、結尾的總結句、只重述標題的句子 | 刪除 |
| 同一個東西在鄰近的句子換不同的名稱 | 全文用同一個名稱 |
| 以「；」連接兩個獨立的陳述 | 拆成兩句，或以逗號與連接詞相連 |

排版依下列規則：

- 中文與英文、數字之間放一個半形空白，全形標點的前後不放空白。
- 指令、路徑、設定鍵、欄名與程式的識別字寫在行內的程式碼。
- 程式碼區塊標明語言，連結寫成有文字的連結。
- 文件與註解使用台灣的用語，政見原文、轉錄稿與原文證據照來源保留字詞、標點與簡繁。

## 程式的檔頭與註解

註解寫規則與理由，數值以設定檔為準。每個分支點上方寫註解，連續的程式每三個邏輯行至少一則註解，註解的句子依 [句子](#句子) 的規則。程式檔的檔頭和它對應的文件用同一組段名，讀者從文件換到程式時找得到同一件事：

| 檔頭的段 | 內容 | 對應文件的章節 |
|---|---|---|
| 摘要與角色 | 這個檔案做什麼、在架構的哪一層 | 文件的第一段 |
| 指令 | 執行這個檔案的指令 | 步驟 |
| 手寫輸入 | 這個檔案讀取的手寫檔 | 輸入 |
| 產物 | 這個檔案寫出的檔案 | 產物 |
| 慣例 | 這個檔案的約定與設計的理由 | 判讀規則、核對 |

<br>

## 檢查

`npm run lint` 檢查根目錄的四份文件、`docs/` 與程式的註解，commit message 與 PR 描述以 `--text` 檢查。修改既有的文件之後另以 `npm run lint -- --grown HEAD` 列出變長的段落、清單項目與表格的格子，逐句確認多出來的內容只講一件事，沒有重複、特例與補述。每筆發現項目列出位置、規則、判定問題與改法，依層級處理：

| 層級 | 意思 | 處理 |
|---|---|---|
| 錯誤 | 程式能精確判定的違規 | 依改法修正，有錯誤時結束代碼是 1 |
| 警告 | 要讀上下文才能判定 | 回答判定問題，答案是「是」時依改法修正 |
| 提示 | 多數時候合理的寫法 | 讀過之後決定要不要修改 |

完成判準如下：

| 條件 | 證據 |
|---|---|
| 沒有錯誤層級的發現項目 | `npm run lint` 的結束代碼是 0 |
| 每筆警告都已回答判定問題 | 修正後的文字，或判定為合理的理由 |
| 每個相對連結的檔案與錨點都存在 | `npm run lint` 的連結檢查 |
